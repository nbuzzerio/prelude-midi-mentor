# Optional local performance audio recording — 2.9.4 implementation handoff

The 2.9.4 implementation is committed at `be243f5`; 2.9.5 is a pending bounded piano extension, October 9, 2026. This was research only in 2.9.3; tagging and release remain owner-controlled.

## Piano extension (2.9.5)

The stable keyboard owner adds `use-piece-practice-keyboard-recording`, constructing a recording-only adapter and the existing native recorder together per run/effect lifetime. Explicit opt-in is the only permission trigger; no analyzer/pitch detector or acoustic analysis session exists. The adapter owns its acquired tracks, lends generation leases to the recorder, requests finalization before release, and cancels late grants. Strict Mode replay, actual cleanup and stale-event isolation follow the 2.9.4 ownership principle. MIDI input/clock/evidence and persistence are independent. Piano filenames and room-microphone metadata use null analysisSessionId and approximate monotonic recording-timeline offsets.

Pause, background/track interruption, opt-out and completion finalize and release capture; resume is an explicit action, never clock-driven acquisition. Restart Measure stays continuous. New/recovered runs default Off. Shared playback/download and audio-loss guards protect every run replacement, focused return and App mode change; stop existing recording playback before acquiring capture. All existing format, budget, memory-only/privacy and final-note-cutoff policies remain. A room microphone may miss headphones-only piano output; VKB recording does not synthesize sound. Physical MIDI integration tests use real input/session owners with fake browser devices; real instrument fidelity and downloaded external-player QA remain owner work.

## Original acoustic ownership (2.9.4)

The monophonic capture controller retains exclusive MediaStream and track ownership in `src/lib/audio/monophonic/microphone-capture.ts`. Optional ready/ending callbacks lend the initialized stream and generation to the Piece Practice recording controller without another microphone request. The Piece Practice acoustic hook owns one capture and one recorder controller per run. Stop, background/freeze/pagehide, muted/ended tracks, interruption, completion and unmount stop tracks. There is no stream-preserving capture pause/resume. Restart Piece replaces the owner; Restart Measure resets input within the same owner. Recovery starts paused with microphone and recording off. Scalar analysis and run evidence/report persistence remain separate.

`features/piece-practice/piece-practice-recording.ts` owns native MediaRecorder negotiation, chunk collection, independent segments, limits and cleanup. Capture alone stops tracks and never waits for recorder finalization. Feature errors leave practice operational. Run V2, IndexedDB, scalar export and report schemas are unchanged.

Capture and recording controllers share one explicit React effect lifetime in the acoustic hook. Effect setup creates a fresh recording controller; cleanup stops its capture, disposes only that recording controller, clears the current-owner refs, and releases its timers, chunks and object URLs. Strict Mode's development setup/cleanup/re-setup therefore cannot leave a disposed controller in use. Stable recording actions consult the current controller ref, while capture callbacks retain their own effect's controller and snapshot publication checks that lifetime is still current. No delayed-disposal timer or additional microphone request is used. Stop Listening within the mounted run still preserves asynchronous finalization and retained segments.

Lifecycle: explicit default-off opt-in begins only during practice, excluding violin preflight. Recorder stop is requested before capture disposal on pause/interruption/completion; final data/stop events arrive asynchronously. Resumed capture creates a separately downloadable segment; independent containers are never concatenated. Restart Measure stays in the same segment if capture continues. New runs need a new opt-in. Finalized segments remain available through completion with local playback/download and a prominent temporary-audio warning. Run replacement, exit and top-level mode navigation require an explicit discard decision while audio is pending or retained. Browser close protection cannot guarantee recovery. Object URLs and blobs are released on owner cleanup. No audio is uploaded or persisted.

Feature-detect `MediaRecorder`; probe `isTypeSupported` for `audio/webm;codecs=opus`, `audio/mp4`/AAC and `audio/ogg;codecs=opus`, then consider the browser default. Use the recorder's actual MIME and matching `.webm`, `.m4a`/`.mp4` or `.ogg` extension; reject unknown types rather than label them MP3. Catch construction/start/runtime failures even after a positive probe. WebKit added WebM/Opus in Safari 18.4, so runtime probing is preferable to browser-name assumptions. Sources: [W3C recording specification](https://www.w3.org/TR/mediastream-recording/), [WebKit Safari 18.4](https://webkit.org/blog/16574/webkit-features-in-safari-18-4/).

Budget: 64 kbps requested audio bitrate, 20 minutes cumulative audio and a soft 16 MiB encoded-data budget with stop requested near 14 MiB. Twenty minutes at the requested rate is about 9.6 MB, but actual bitrate and event delivery vary. Roughly one-second chunks and monotonic elapsed time are counted independently. Final overshoot is retained and reported. No silent eviction or strict browser heap guarantee. Existing immediate completion can truncate the final note; no duration grading or post-completion tail was added.

Device QA remains required: Chrome/Chromebook/Android, Firefox and Safari/iOS playback/download, background interruption, long takes, memory limits, tone fidelity, controls at 200% zoom and mobile browser termination. Automated tests cover native format selection, shared stream, delayed final events, segment boundaries, limits, cleanup and navigation. No MP3 transcoding, waveform editor, audio persistence or sustained-note grading.
